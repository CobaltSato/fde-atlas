## 1. 機能した設計（実証できたもの）

- **点検の道具化（`/verify-report` 相当）が、規範では止まらなかった欠陥を実際に止めた。** 導入後の初回実行で3件、以降のセッションでも既存欠陥を継続的に検出した（分母の誤り・割合表記の誤り等）。前期のFB 2.8「Skill昇格は接続点が無いと起きない」への対策が、実際に1件の昇格として結実した。

## 2. ガイド・テンプレへの改善提案

### 2.0 【改訂規範】厚くしない — 規範には「失敗の型」を書き、手順は Skill へ逃がす

第1期・第2期を通じ、**規範として書いたものは実行されず、道具として置いたものは実行された**。棚卸しは目安の3倍を超えても発火せず（機械チェック導入で発火）、点検は6セッション連続で失敗してようやく道具化された。一方で、規範の側にあって効いたものは「承認線」「可逆性判定」「SoR」のような**判断の前提**と**止まる境界**であり、手順ではなかった。

厚いハーネスは柔軟性を縛り、想定外の業務で身動きを取れなくする。だが**汎用的なベストプラクティスに最低限従わせるための薄いハーネスは有用**である。両立の線引きは:

| ハーネス（ガイド）に書く | Skill・checklist へ逃がす |
|---|---|
| 高くつく失敗の型（何が・なぜ内側から見えないか） | 手順の詳細・コマンド・順序 |
| 止まる境界（承認線・可逆性・停止線） | ツールのクセ・環境固有の罠 |
| 判断の前提（SoR・作業地図・自律度） | 業務ごとの様式・記入例 |

**提案**: §1 へ改訂規範として新設する。①規範は「やり方」ではなく「失敗の型」を書く（やり方は状況が変わると誤りになるが、失敗の型は効き続ける）②MUST を増やす前に Skill へ落とせないかを検討する（業務を跨いで効くものだけを規範へ）③1項目足したら古い1項目を消せないか見る（改訂は追記でなく再構成）④**迷ったら書かない**（書かれていない領域はAIが判断してよい領域。判断が繰り返し割れたときだけ昇格させる）。
**本FB自体もこの規範に従い**、以下の提案は「型」だけをガイドへ、手順はすべて Skill・checklist へ振り分けている。

### 2.1 【最重要】「測定する道具そのものが壊れている」欠陥クラスが規範に無い（§7.6・§9）

シミュレーション内の一類型の実装が、意図した挙動（自分の推定に従って行動する）と逆の挙動（自分の推定を捨てて市場の逆に張る）になっており、**ある要件を「測れていなかった」**。結果として1つの方式の評価が反転し、確定値の全面差し替えに至った。

この欠陥の性質が重要である:

| 性質 | 内容 |
|---|---|
| **試行数を増やしても消えない** | 全試行に同じくかかるバイアスであり、母数拡大（20本→10000本）でも消えない。むしろ「識別できる」判定が**強く**なり、誤った結論への確信が上がった |
| **成果物どうしの照合では検出できない** | 全成果物が同じ壊れた値を正しく引用しているため、突き合わせは全一致する |
| **集約値は自然に見える** | 平均・SE等の集約統計は、壊れていても異常に見えない |
| **発見経路は人間の直感だった** | 人間の「それは変では?」という指摘が起点。AIは2度、方式固有の性質のせいだと**誤説明した** |

既存の §7.6（数字の規律）は「合計を再計算で照合する」「単位を確認する」という**転記・計算の正しさ**の規範であり、「その指標が測ろうとしているものを本当に測っているか」という**妥当性**の規範が無い。§9 の捏造禁止も「存在しない数値を出すな」であって、「存在するが無意味な数値」は対象外である。

**提案**: §7.6 に「指標の妥当性」の項を新設し、以下を規範化する。
1. **指標を追加・変更したら、「この指標が測ろうとしている要件文を、コードのどの行が体現しているか」を1行で書けるか確認する。** 書けなければ、まだ測れていない。
2. **集約値の外側の量を1回は目視する。** ペルソナ・エージェント・分類器など「振る舞う要素」を含む計算では、その振る舞いが意図どおりかを、最終指標ではない別の量（的中率・分布・個別事例の数件）で確認する。
3. **試行数の拡大は妥当性の証明ではない。** 「ばらつきが小さいこと」と「正しいものを測っていること」は独立である。母数拡大で強まるのは前者だけであり、後者が壊れていれば誤った結論への確信だけが上がる。
4. **人間の直感的な違和感は、AIの説明が筋を通していても優先して検証する。** AIの説明能力は、欠陥を合理的に説明してしまう方向にも働く。

### 2.2 数値成果物の点検は「対象一覧（manifest）」から始める（§9.7・新規Skill）

同一のコード出力を引用する成果物が複数ファイルに散る構造では、grepでも手順書でも防げない失敗が4パターン観測された。

| # | 失敗 | なぜ手順書・grepで防げないか |
|---|---|---|
| 1 | 表は差し替えたが**地の文が旧値** | 地の文は「3.5個分」「そちら側」等の**言い換え**で書かれ、数値検索に載らない |
| 2 | 生成物は直したが**生成元スクリプトが旧値** | 次回の再生成で**旧値が復活する** |
| 3 | 同一ファイル内で**既訂正の記述と自己矛盾** | どちらも「正しい文」に見える |
| 4 | 資料Aは直したが**資料Bが取り残された** | 対象一覧が無いので**そもそも見に行かない** |

**4が最も危険**で、かつ手順書の改善では直らない（「全部見る」と書いても、何が全部かを知らない）。対策は**点検対象を列挙した正本ファイル（manifest）を持ち、点検はその読み込みから始める**こと。

**提案**: ①テンプレ同梱の Skill として「数値成果物の点検」を追加し、`manifest.md`（点検対象の一覧＝正本）を必須構成要素にする。②点検手順に「記録値ではなく**コードの再実行結果**と突き合わせる」「**生成元スクリプトも対象に含める**」「数値検索だけでなく**主張文のキーワード**（『個分』『満たす』『上回る』『唯一』等）でも洗う」「修正後に**再照合**する（直した値が正しいとは限らない）」を明記する。③停止線として「**歴史的記録（指示書・過去の決定メモ・アーカイブ）は書き換えない**」を置く。これらは当時の状態を正しく述べており、一括置換すると記録が壊れる。「旧値が残ってよい場所」と「現在の状態を語る文」の区別が必要。

### 2.3 点検の「基準側」の欠陥は、その点検道具では原理的に検出できない（§9.4）

点検道具の導入後、**manifest（基準）自身に欠陥があった**実例が出た（ある指標だけ異なる母数の値が基準表に載っており、確定値表の中で母数が混在していた）。成果物どうしの照合しかしない道具は、基準が間違っている場合を検出できない。これは道具の不備ではなく**構造的な限界**である。

**提案**: §9.4（実行記録で検証する）に「**検証道具の限界を、道具自身に明記する**」を追加。具体的には ①「この道具で検出できないもの」を Skill 本文へ1節として書く ②**基準側を書き換えるときは、記憶や既存記録からではなく供給元を再実行して値を取り直す** を規範化する。あわせて §13.4 の失敗パターン診断表へ「点検を通ったのに誤りが残る → 基準側の欠陥・妥当性の未検証 → §7.6 の指標妥当性・manifest の再実行」を追加。

### 2.4 「注釈が要る名前」は失敗した名前である（文書規範）

ある選択肢の名称が指示語を含んでいたため（「現行」＝当初案の意味で使っていた）、報告物に「ここでの『現行』は当初案の意味」という**防御的な注釈**が付いていた。注釈で運用を続けるのではなく、指示語を廃した実体を表す名前へ改名して解決した（11箇所）。

**提案**: 文書規範へ「**注釈を足さないと誤解される名前は、注釈ではなく改名で直す**」を追加。指示語（現行・新・旧・今回）を含む固有名は、時間が経つと意味が反転する。§4（Context Layer / glossary）に「名前の付け替えは、注釈より安い」を明記する。

### 2.5 AI自身が難語・独自語を持ち込む欠陥（文書規範の追補）

読者向け成果物の改稿で、**AIが自分で難語を持ち込む欠陥が1セッション中に3回**発生した。①コード内部の変数名をそのまま読者向け説明へ投入 ②数式をそのまま提示 ③同じ語（「ばらつき」）で異なる2つの量（1回ごとの散らばりと平均のブレ）を指してしまい混乱を生んだ。さらに、説明を足し続けた結果1セルが592文字へ肥大した（3件目は自作チェッカーが検出）。

前期FB 2.4 は「AIの検討履歴・内部プロセスを混ぜない」だったが、これは**内部の語彙を混ぜない**という別軸である。

**提案**: checklists の成果物レビューへ ①**読者が知らない語を新たに導入していないか**（コードの変数名・専門記法・数式をそのまま出していないか）②**1つの語が2つの量を指していないか**（同語異義の自己混入）③**説明を足す方向にだけ動いていないか**（分量の上限を決め、超えたら再構成する）を追加。前期2.4の「短縮依頼＝再構成であって削除ではない」と対になる規範として、「**説明の追加も再構成であって、追記ではない**」を置く。

### 2.6 結論が正しくても、その「理由」が捏造されることがある（§9 捏造禁止の追補）

評価表の判定記号（正しい）に対して、その**理由**を誤って記述した実例が出た（原典では「価格が単純比率で情報加重がない」ことが理由なのに、「ある値を捨てているから」と書いた）。原典との照合で訂正。判定そのものが合っていたため、**結論を見るだけのレビューでは通ってしまう**。

§9 の捏造禁止は「存在を確認していない数値・リンク・条項・出典を出力しない」だが、**因果・理由の捏造**が明示されていない。もっともらしい理由付けは、結論が正しいときに最も検出されにくい。

**提案**: §9 の規則へ「**MUST NOT: 理由を捏造しない。** 判定・結論に理由を添えるとき、その理由が原典に書かれているかを確認する。原典が理由を述べていなければ『原典は理由を述べていない』と書く。結論が正しくても理由が誤っていれば、その資料は次の判断を誤らせる」を追加。あわせて成果物チェックリストへ「判定と理由を**別々に**原典照合したか」を追加。

### 2.7 「実装の指示」ではなく「設計の必須項目」を渡す型（§6・承認線）

ある方式を採用する場合にのみ発生する設計課題（3件）を、**要件を変更せずに**「採用時の引き受けリスト」として別立てで資料化した運用が機能した。要件の判定記号を動かさずに（＝運用上の理由で選択肢を落とさずに）、判断材料だけを増やせた。

**提案**: §6.3 の承認線の説明へ、「**要件で拾えない考慮事項は、要件を書き換えるのではなく『採用時の引き受け項目』として分離する**」を実務パターンとして追加。要件を後から書き換えると過去の判定との比較可能性が失われる。あわせて「評価軸を追加するか」自体を未決事項として記録し、人間承認へ回す形（本件では3択で記録）を §14 の承認依頼形式の変種として示す。

### 2.8 計測ログの「差し戻し」列は、原因の型まで書くと原資になる（§12.1）

前期FBで有効性が確認された計測ログだが、第2期では差し戻し欄に**原因の型**（「自分が前セッションで出した提案を欠陥由来と認めて取り下げ」「正本の側に旧値が残っていた」等）が書かれるようになり、本FB全体の根拠になった。有無だけの記録では、ここまでの分析はできなかった。

**提案**: §12.1 の計測ログ形式へ「差し戻しは**有無でなく型**を1行で書く」を明記（例: 反映漏れ／前提の誤り／読者定義の欠落／測定の妥当性）。列を増やすのではなく、既存列の記入粒度の指定として置く。

### 2.9 セッション中断への耐性は「段階ごとのcommit」で実証された（追認）

利用上限による中断が複数回発生したが、段階ごとのcommitと STATUS の「次の一手」により、いずれも再開できた。第2期では **1セッションが2分半のコード実行を複数回含む**構成になり、長時間化した。

**提案**: §5.4 へ「実行に時間のかかる処理（数分規模の再計算・再生成）を含む作業は、**実行の前後で必ずcommitを切る**」を追加。あわせて Skill へ**所要時間の実測値**を書く（本件では『本走 約2分半・再生成 約1分15秒。タイムアウトを短く切らない』が Skill に記録され、実際に有効だった）。**道具の所要時間は、道具の一部として記録する。**

### 2.10 未使用の同梱資産は死蔵し続けた（前期2.10の追認と補強）

前期に指摘した「未使用の同梱資産（台帳・registry等）」は、第2期でも稼働しなかった（台帳は2件のみ、`registry` は未使用のまま）。一方で、**案件の必要から生まれた資産（点検 manifest・指示書・アーカイブ）は自然に育った**。

**提案**: テンプレ同梱資産を「**最初から使うもの**」と「**必要になったら作るもの**」へ二分し、後者は空ファイルを置かず README で存在だけ案内する。空ファイルが置かれていると、棚卸しのたびにノイズになり、かつ「使っていない＝不健全」という誤った罪悪感を生む。

## 4. 次の観測ポイント

- 2.1（指標の妥当性）を規範化した後、「測定対象そのものの欠陥」が着手前に検出されるか。それとも人間の直感が引き続き唯一の検出経路か。
- manifest 方式（2.2）を他の点検（文書の整合・リンク切れ）へ横展開できるか。
- 2.5（内部語彙の混入）は、チェックリストで止まるか、それとも読者役のレビュアーを別に立てる必要があるか。
