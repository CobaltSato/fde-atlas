## 3. `design/2026-08-04-desk-design.md`（desk/ 構想）

**状態は「提案（人間の承認待ち）」です。** Q1〜Q4 の回答欄は空欄で、template/ に `desk/` も `review-ticket.md` もまだありません。

- **動機**: 2期の運用を通じて、人間のレビュー負荷がボトルネックになりました。人間が見るべきものが、STATUSの手作業待ち、work/ 内の承認依頼と質問、docs/（レビュー待ちと確定済みが混在）、会話の末尾、の4箇所以上に散っています。その結果、人間は「全部見るか、見落とすか」の二択になり、承認依頼も全文の貼り付けで重くなっていました。
- **結論の4点**:
  1. 人間が開く場所を `desk/` と `docs/` だけにし、残りはAIの作業場で「開かなくてよい」と宣言する。
  2. 人間に見せたいものは desk/ 経由でしか出せないようにする（承認線を物理的な置き場にする）。
  3. レビュー票の型を強制する：判断点は3点以内、Yes/No の問い、Mermaid 図は必須、全文はリンクで示しコピーは禁止。
  4. 「絞る」は判断点の数を絞ることで、説明を削ることではない。票はリンクを開かなくても判断できるように完結させる。
- **構造**: `desk/TODAY.md`（/wrap-up が作り直すダッシュボード。判断待ちを1行ずつと、現在地のMermaid）と `desk/a-NNNN-<件名>.md`（1件1ファイル、回答欄に直接書く）。
  - 報告だけのものは票にせず、TODAY.md の1行に留める。
  - 回答済みの票はAIが `work/<業務>/archive/` へ移すので、「desk/ に残っている＝未回答」が常に成り立つ。
  - 7件を超えたらフックで警告する。
- **運用の流れ**: AIが承認線に達したら票を置き、他の作業を続けるか止まる。人間が TODAY.md から票の回答欄に記入する。次のセッションでAIが回収して実行し、票を archive へ移す。
- **反映先**: ガイド §6（会話だけの承認依頼は禁止）と §10（票の型）、AGENTS.md §11、wrap-up（STATUSの手作業待ちを desk/ へ移す）、README（「見るのはこの2つだけ」）、install.sh。
- **移行方針**: 既存ディレクトリは動かさず、新設と宣言だけで分離します。**資産を純増させないため、approval-request.md を review-ticket.md に統合して廃止します**（2fed9a5 で追記）。避難訓練の経路は残します。
- **未決の問い**: Q1 2箇所に絞るか、Q2 報告は1行に留めるか、Q3 名前は `desk/` か（代案は `for-human/`・`inbox/`）、Q4 実装に進むか。

  - Issue と PR を歓迎。
  - バグは再現手順・期待した動作・実際の動作を書く。機能提案は Why（業務シーン）から書く。
  - PR の手順：Fork、`template/` を変えたら install.sh への影響を確認、日本語で統一、Conventional Commits。
  - **fde-guide.md や AGENTS.md の安全設計（承認線・自律度・機密）を変える場合は、先に Issue で議論する。**
- `.github/ISSUE_TEMPLATE/bug_report.md`：症状、再現手順、期待した動作、実際の動作、環境（OS、Claude Code のバージョン）。
- `.github/ISSUE_TEMPLATE/feature_request.md`：困っている業務シーン、提案、代替案。
- PRテンプレ、CI、lint はありません。
- 実際の改訂は外部からの Issue ではなく、**所有者の現場FBを `design/feedback/` に一般化して置き、そこからガイドとテンプレを改訂する**流れで回っています。

## 8. まとめ：V2で残すもの・削れるもの

**V2で残すもの（実運用で裏付けがあるもの）**
1. **承認線、可逆性、SoR、指示混入の防御**。FB2 2.0 は、規範の中で効いたのは判断の前提と止まる境界だった、と明言しています。K01（指示混入の検知）も実機で合格しました。ここは汎用で、V2の薄い中核にそのまま使えます。承認線には「評価枠組みの確定」も含めます。これは FB1 2.3 で最大の手戻りを防いだ項目で、操作系に偏らない汎用化の鍵です。
2. **状態ファイルと段階ごとのcommitによる再開**。中断からの再開は2期連続で実証されています。ただし、**上限は機械で強制**します（バイト上限、8KB警告、アーカイブへ退避して削除しない）。
3. **規範ではなく仕組みで発火させる**。棚卸しも、Skill昇格も、点検も、規範に書いただけでは動かず、フックや道具を置いて初めて動きました。V2では、規則を書くなら発火装置と一緒に置くことを原則にします。昇格の引き金は「同型の失敗2回」です。
4. **§1.6 の改訂規範そのもの**（失敗の型だけを書く、迷ったら書かない、1つ足したら1つ消す）。V2のガイドの編集方針として最初に置くべき内容です。v2.3〜2.5 ではこの規範を書きながらガイドが行数ベースで純増し続けたので、V2では行数の上限など機械的な縛りが要ります。
5. **汎用の失敗の型**：理由の捏造禁止、指標の妥当性（人間の違和感を優先する）、読者定義（内部プロセスや内部語彙を混ぜない、「短く」も「説明を足す」も再構成で行う、名前は注釈でなく改名で直す）、計測の差し戻しは原因の型で書く。どれも業務の種類に依存しません。
6. **人間のレビュー負荷を設計の対象にする**（desk/ 構想）。approval-request は使用0件、手作業待ちは STATUS に置いたら機能しました。人間側の入口を1つにまとめることは、非エンジニア向けの汎用ハーネスの中心になります。

**V2で削れるもの（推測で足して検証されていないもの）**
1. **validated されていないスキル7本**（brainstorm、wrap-up、design-doc、setup、skill-create、cleanup、model-change）。validated が入っているのは filing・minutes・research の3本だけで、それも7/11の架空データによるものです。
   - さらに **K01 の期待値は「台帳の記入例と照合して重複と判定」ですが、その記入例を含む ledger.md は 2fed9a5 で削除されました。** 回帰の前提が壊れていて、今は再現できません。
   - K04 と K05 は未実行のままです。
   - SI寄りのスキル（design-doc、filing）と、SI設計書テンプレ（requirements、basic-design）は、一般の業務には特化しすぎています。
2. **台帳類と組織向けの章**：Registry（§13.1）、ROI・移管・自走判定（§12）、流行語の読み替えと Ontology（§4.3〜4.5）、§14.3〜14.7 の参照だけの節。実際に死蔵していたか、AIの行動に影響しない読み物です。ガイドの外の解説へ出すのが妥当です。
3. **§11 の実務パターン集と §9.7・§11.8 の具体的な手順**。これらは案件依存（請求書、freee、数値 manifest）なので、Skill 化するかオプションの同梱に回します。FB2 自身も「手順は Skill へ」と言っています。
4. **モデル交代の重い儀式**：registry、6項目チェックリスト、運転モード、年1回の避難訓練。どれも未検証です。V2では「回帰ケースを数件、弱いモデルで回す」まで縮めるのが現実的です。
5. **古い説明資料の同期コスト**：kaisetsu.html（v2.1のまま）、blueprint（7/11で止まっている）、ガイドの改訂履歴の漏れ（2.5の行が無い）、AGENTS.md の版数の漏れ（v2.4の時に修正し忘れ）。V2では二重管理を減らします。説明は1箇所にまとめ、版数はガイドの1箇所だけに持たせます。

**参考になる数字**: AGENTS.md は154行・5,153字（上限は5,500字）、template/ は47ファイル・196KB、ガイドは1217行です。V2の「薄さ」を測る比較の基準にできます。
